# Bank Model-Risk KG — schema

A synthetic model-risk inventory for a mid-size bank, designed so the governance
questions in `queries/governance-queries.cypher` are first-class graph traversals
rather than multi-table joins.

## Node labels

| Label | Key properties | Meaning |
|-------|----------------|---------|
| `Model` | `id, name, category, tier (1–3), status, regulatory_use, methodology, last_validated` | A model in the inventory (PD/LGD/EAD, IFRS9 ECL, CCAR, AML, fraud, market risk, LLM screening, …) |
| `DataSource` | `id, name, type, system, sensitivity, refresh` | A system/feed a model consumes |
| `Feature` | `id, name, data_type, pii` | An engineered input; derived from a `DataSource` |
| `Assumption` | `id, description, category, status` | A modelling assumption (Macro/Behavioral/Statistical/Operational) |
| `Validation` | `id, outcome, type, date` | An independent validation event (Initial/Annual/Ongoing) |
| `ValidationFinding` | `id, title, category, severity, status, raised_date` | An issue raised by a validation |
| `RegulatoryRequirement` | `id, framework, clause, title` | A regulatory obligation (SR 11-7, Basel III, IFRS 9, ECB TRIM, EU AI Act, RBI, CCAR/DFAST, BCBS 239, FRTB) |
| `Control` | `id, name, type, frequency, status` | A governance/detective/preventive control |
| `Person` | `id, name, role` | Owner / validator / model-risk officer / developer / CRO |
| `BusinessUnit` | `id, name` | Owning business line |
| `Submission` | `id, name, regulator, frequency, next_due` | A regulatory submission (CCAR 2026, DFAST, IFRS9 ECL, ICAAP, AML SAR, Pillar 3) |
| `Decision` | `id, name, type` | A business decision a model drives |

## Edge types

| Edge | From → To | Meaning |
|------|-----------|---------|
| `OWNED_BY` | Model → Person | Accountable owner |
| `DEVELOPED_BY` | Model → Person | Developer |
| `BELONGS_TO` | Model → BusinessUnit | Owning line |
| `MEMBER_OF` | Person → BusinessUnit | Org membership |
| `DEPENDS_ON` | Model → DataSource | Direct data dependency |
| `USES_FEATURE` | Model → Feature | Input feature |
| `DERIVED_FROM` | Feature → DataSource | Feature lineage |
| `MAKES_ASSUMPTION` | Model → Assumption | Stated assumption |
| `GOVERNED_BY` | Model → RegulatoryRequirement | Applicable regulation |
| `SATISFIES` | Control → RegulatoryRequirement | Control ↦ requirement mapping |
| `CONTROLLED_BY` | Model → Control | Applied control |
| `EVIDENCES` | Validation → Control | Evidence for a control |
| `VALIDATED_BY` | Model → Validation | Validation event |
| `PERFORMED_BY` | Validation → Person | Validator |
| `RAISED` | Validation → ValidationFinding | Finding raised |
| `FEEDS` | Model → Model, Model → Submission | Upstream risk parameter feeds an aggregate model / a submission |
| `USED_IN` | Model → Decision | Drives a decision |

## Why these shapes

- **Lineage / blast-radius** — `Model -DEPENDS_ON-> DataSource` and `Feature -DERIVED_FROM-> DataSource`,
  plus `Model -FEEDS-> Model -FEEDS-> Submission`, make "if this feed changes, what breaks?" one traversal.
- **Regulatory mapping** — `Model -GOVERNED_BY-> RegulatoryRequirement <-SATISFIES- Control` keeps the
  requirement→control→evidence map live.
- **Explainability** — `Model -USES_FEATURE-> Feature -DERIVED_FROM-> DataSource` is the replayable
  audit path behind a model's decision.
- **Audit readiness** — `Model -VALIDATED_BY-> Validation -RAISED-> ValidationFinding` surfaces open,
  high-severity gaps on critical (Tier-1, production) models.

All data is generated by `etl/generate.py` from a fixed seed — no real institution, no PII.
